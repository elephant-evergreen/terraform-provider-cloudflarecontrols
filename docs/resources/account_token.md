# cloudflarecontrols_account_token (Resource)

Issue and manage a Cloudflare account-owned API token. The token value is stored in Terraform state when created.

## Issue a token

1. Configure encrypted storage for Terraform state and saved plans. Grant
   access to the people and runners allowed to use the issued token.
2. Authenticate Terraform with **Account → Account API Tokens → Edit**
   (`Account API Tokens Write` in the API). The issuing identity also needs
   the permissions it intends to grant.
3. Find the ID of the **DNS Read** permission group with the [List Permission Groups](https://developers.cloudflare.com/api/resources/accounts/subresources/tokens/subresources/permission_groups/methods/list/)
   endpoint (`GET accounts/{account_id}/tokens/permission_groups`). Replace the
   synthetic account, permission group, and zone IDs below and choose an
   expiration.

See the [Cloudflare permission and scope reference](https://developers.cloudflare.com/fundamentals/api/how-to/create-via-api/) for how permissions combine into a token policy.

```terraform
resource "cloudflarecontrols_account_token" "dns_reader" {
  account_id = "00000000000000000000000000000000"
  name       = "Read DNS for one zone"
  expires_on = "2030-01-01T00:00:00Z"

  policies = [{
    effect = "allow"
    permission_groups = [{
      id = "11111111111111111111111111111111"
    }]
    resources = jsonencode({
      "com.cloudflare.api.account.zone.22222222222222222222222222222222" = "*"
    })
  }]
}
```

After apply, pass the resource's `value` directly to its intended consumer.
Terraform retains the issued bearer token in state and can include it in
saved plans. Store state and plans in an encrypted backend or other encrypted
storage and restrict access. Avoid exposing the token in a root output or in
debug and CI logs. [Terraform sensitive state](https://developer.hashicorp.com/terraform/language/manage-sensitive-data)

## Adopt an existing token

Match the token's current settings, then use its account ID and token ID.

```sh
terraform import cloudflarecontrols_account_token.dns_reader ACCOUNT_ID/TOKEN_ID
terraform plan
```

Use `Account API Tokens Read` for adoption and refresh. Cloudflare only
returns the token secret on issuance or explicit rotation, so import leaves
`value` empty. Destroy revokes a token immediately. To replace a token in use,
issue a separate token, switch its consumers, and verify them before revoking
the old one.

## Move from the Cloudflare provider

For an existing `cloudflare_account_token` with state schema 501 (verified
with Cloudflare provider v5.28.1), Terraform 1.8 or later can move the existing
ID and stored value.

1. Confirm that your secured backend retains the state version before the
   move so you can recover it.
2. Add Cloudflare Account Controls to the module's provider requirements.
   Pass the provider configuration to child modules that use it.
3. Change the resource type and its references. Remove an explicit `status`
   argument if present and omit an empty `condition` object. Preserve any IP
   restrictions you configured.
4. Add the moved block below in the same module, then run `terraform init`.

```terraform
moved {
  from = cloudflare_account_token.dns_reader
  to   = cloudflarecontrols_account_token.dns_reader
}
```

Run `terraform plan`. Check that the token is moving to the new address
and that none of its attributes change. Terraform can count a move as one
update even when the attributes match. In that case, the provider only
records the new address. Stop before applying if the plan proposes creating,
destroying, or changing the token, or reports an unsupported source schema.

Apply the reviewed move and run `terraform plan` again. Expect no changes.
